# Architecture

Nuclear Triad is a client-only BepInEx 5 plugin that renders Nuclear Option as three correctly projected views, one per physical screen, instead of one camera stretched across all three. This is how it does that. The game-side facts it relies on are in [game-internals.md](game-internals.md), and the build and dev loop in [developing.md](developing.md).

## Cameras

- The center view is the game's `mainCamera`, with its viewport rect shrunk to the center monitor. Each side view is a new camera parented to the main camera at zero local offset. Its local rotation is the panel's orientation: yaw, plus pitch and roll if the panel is tilted.
- Before each render, copy the main camera's settings onto the side cameras: clip planes, culling mask, layer cull distances, clear flags, HDR/MSAA, and the URP `UniversalAdditionalCameraData` fields. Copy them rather than hard-coding.
- Each panel is a rectangle in eye space, in millimetres, with the eye at the origin, +x right, +y up and +z forward. Kooima's generalized perspective projection turns that into a frustum. The camera transform faces the panel, and only the off-axis frustum goes into `projectionMatrix` via `Matrix4x4.Frustum`. Never bake rotation into the projection.
- All three cameras use the geometry-derived frustum, the center included. While the rig is on, the game's FOV and zoom are overridden.
- Unity view space is right-handed (the camera looks down −Z), while world and local space are left-handed. A sign slip mirrors the side views, and the geometry tests catch it.

## Geometry settings

- Geometry controls work like iRacing's and Assetto Corsa's. Each side screen gets its width, its angle off the center screen's plane, and the pixel-to-pixel gap at its seam; heights follow from width and pixel aspect. Those are the simple settings.
- Each screen's `WidthMm` starts at the picture width its monitor reports to Windows (EDID, read per display with `GetDeviceCaps`; `Geometry/ScreenSize.cs` checks the report against the pixel pitch and guesses from the pixel count when it fails), so a new install is close before anyone measures (0.1.29). Up to 0.1.28 the defaults were the development rig's panels, 392, 697 and 392 mm, which a first install on three 797 mm ultrawides got as values.
- By default the eyes are level with the center screen's middle, the center screen keeps the game's own FOV framing (`Geometry.CenterFraming = GameFov`), and side screens are vertically centered on the center screen. The eye height (`Geometry.EyeHeightMm`) is a simple setting, and the tuner's step after the widths. In either framing, the center screen draws straight ahead at that height, so a level horizon sits at eye level; 0 is vanilla.
- Each side's vertical offset (`VerticalOffsetMm`, tuned with the horizon) is a simple setting, and taking it from the Windows arrangement is advanced. Physical eye distance, the eye's sideways offset and pixel rects are advanced settings, hidden behind F1's "Advanced settings" box. So is each side screen's `PhysicalAngleDeg`: its real angle, for when `AngleDeg` holds a tuned value instead, as game-FOV framing's tuning gives (11° on the development rig, against a real 35°). Only the flight HUD's Physical size on the wings uses it.
- Two different things set a side screen's vertical placement. The Windows display arrangement decides which of the side screen's rows the window lights (the band): the window covers the center screen's desktop rows. `VerticalOffsetMm` tells the projection where the screen physically sits. The frustum follows whichever rows are lit, so the image is right either way; but the band only looks level with the center screen when the Windows arrangement matches the physical one. Window UI such as the flight HUD is drawn in window pixels, so a piece straddling a gap splits by the same offset. `tools/align-screens.ps1` lines the arrangement up with the screens by eye; drawing the HUD per screen, planned, would remove the dependence.
- Which display is which screen (0.1.28; `RigConfig.Resolve`): a screen's `PixelRect` if set, else the display its `Monitor` names. A blank `Monitor`, the default since 0.1.28, follows Windows' arrangement: the one display with exactly one display beside it on each side (touching that edge, sharing some rows) is the center, and those two are left and right (`Geometry/DisplayRow.cs`). With none or several, as with four in a row, nothing is guessed. Up to 0.1.27 the defaults were DISPLAY2, DISPLAY1 and DISPLAY3, the development rig's numbering, and BepInEx wrote them into every cfg as values, so the tuner's out-of-order note is what catches those.
- Numeric geometry settings have ranges, so F1 shows sliders and clamps every edit. A layout that is in range but still can't be drawn (the eye behind a screen, say, after an eye offset past a seam) doesn't stop the rig. The rig keeps the last layout that worked, warns once in the log and puts a notice on the center screen, and it follows the settings again as soon as they can be drawn. The layout fail-safe, which switches the rig off until it's toggled back on, is only for unexpected errors.

## The geometry model

- Each screen is a flat rectangle in eye space: millimetres, eye at the origin, +x right, +y up, +z forward.
- The center screen sits square to the eye at the measured distance, shifted by the eye offsets.
- A side screen's inner edge sits at the measured gap from the center's edge pixel. The gap is split evenly between the two screens' planes, so the straight-line distance between the edge pixels equals the measured gap. The side screen then turns toward the eye by its angle about that seam.
- Height = width × (vertical pixels ÷ horizontal pixels), from the screen's current resolution.

### How the tuner's lines show each setting

Each row below changes one setting from tuned values (11.0°, 80 mm, +10.3 mm). The model looks at the right gap in game-FOV framing, from a real eye at 750 mm, with the side screen physically at 35°. A step is how far a line sits, where it comes out of the gap, from where it would run on straight. A bend is how far it then turns away over the side screen's first 150 mm. Both are in degrees, + up. The cyan line is the one climbing toward the side screen. Each cell gives the step, then the bend.

| Change | Yellow line | Cyan (+30°) | Green (−30°) |
| --- | --- | --- | --- |
| None: the tuned values | 0, 0 | −0.05, +0.16 | +0.05, −0.16 |
| Angle 5° too big | 0, 0 | +0.02, +0.38 | −0.02, −0.38 |
| Gap 10 mm too big | 0, 0 | +0.22, +0.15 | −0.22, −0.15 |
| Vertical offset 3 mm too high | −0.20, 0 | −0.24, +0.16 | −0.13, −0.16 |
| Eyes 30 mm above the eye height set | −0.07, −0.23 | −0.11, −0.05 | −0.01, −0.37 |
| Eyes 30 mm right of center | 0, 0 | −0.03, +0.25 | +0.03, −0.25 |

The yellow line responds to only two settings. A wrong eye height bends it, down past the gaps when the eyes sit above it. A wrong vertical offset steps it. Its height on every screen is the eye height less that screen's offset, whatever the angles and gaps. A wrong gap steps the sloping lines opposite ways, and a wrong angle bends them opposite ways. A wrong eye height bends both the same way, which no angle setting straightens; that's why it comes before the gaps and angles. A sideways eye offset bends them opposite ways, like a different angle, so the per-side angles take it up and the tuner leaves `EyeSideMm` alone. A wrong eye height shows only weakly: 30 mm makes about a quarter of a degree over 150 mm, growing toward the side screens' far edges. So the step starts with looking straight ahead, or measuring, and uses the bend to finish.

## The on-screen tuner

The tuner (`Tuning/`) is a mouse panel on the center screen. It walks through the three screens' widths, then the eye height, then the side screens' vertical offset, gap and angle, with the sides linked by default; linked, both get the same change.

- The widths come first because every later value is in millimetres on screens the widths size, and no line can show them. The step lists each screen's width beside what its monitor reports (with a Use it button), and draws a yellow bar of a stated length (300, 200 or 100 mm, `ScreenSize.RulerMm`) at the top third of every screen, so a tape measure checks the width without finding edge pixels; longer than stated means press + (0.1.29).
- Its lines are fixed to the view, so they work parked: an eye-level line with a ring straight ahead, and lines through each gap at ±30°. The step order follows what each setting does to those lines (`Geometry/TuningLines.cs`, and the model above). They sit on the cockpit's layer 2 m out, so they draw over the canopy frames.
- While it's open it shows the cursor, which the game takes as a reason to pause cockpit mouse look and, with its menu weapon safety on, to hold fire. Changes save as they're made; Revert restores the values from when it opened.
- While the rig isn't built, an amber note under the step's heading says why and what to do (0.1.25). It covers a screen's `Monitor` that matches no Windows display, or a blank one with no row of three to follow, listing Windows' displays left to right; `Rig.Enabled` off; the rig switched off, by the hotkey or the fail-safe; no mission yet; and `Rig.CockpitOnly` outside the cockpit view. A small Screens line under it always names the display each screen uses, and where that came from (0.1.28). When the three are out of left-to-right order in Windows' arrangement, or two share a display, the amber note says so first, built or not: the views are then likely on the wrong screens.

## HUD and UI

- **HUD markers.** One Harmony postfix (`Patches/MainCameraScreenPointPatch.cs`) on `Camera.WorldToScreenPoint(Vector3)`, the call every window-HUD marker uses. While `Hud.SideScreenMarkers` is on and the rig is built, the main camera's answer for a point on a side screen comes from that side camera. A point in a bezel gap is held at the seam, and one beyond a side screen gets that camera's answer, off the window's edge, for the off-screen arrows. `hud-check` measures it on the game's own markers.
- **Eye hold** (`Rig/EyeHold.cs`, behind `Rig.HoldEyeInFreeLook`, on by default). Past about 33° of pan, cockpit free look slides the eye sideways, like leaning, up to 20 cm at 100°. On the wings that makes the near cockpit shift under the flight HUD. Late in the frame, the sideways part of the camera's local position is replaced: no slide while the nose is still on a screen, then the game's ramp from the outermost edge (`Geometry/FreeLook.cs`). Head trackers are left alone.
- **Flight HUD** (`Rig/HudBender.cs`, behind `Hud.BendFlightHud`, on by default). The game anchors its ladder, heading tape and readouts at the screen point of the aircraft's nose, in Update, before it moves the camera in LateUpdate, so the HUD trails a turning view by a frame. Late in the frame (order 10000, after the camera manager at 2), the bender places the anchor, roll and velocity vector again with the camera as it will render. When the anchor is on a wing, it turns the group's own parts about the anchor to the wing's local horizontal there. It sizes them per `Hud.BendScale`: Physical (default), as big from the real eye (`Geometry.EyeDistanceMm`) as on the center screen; Rendered, the wing's own scale; or None. It leaves alone parts that other scripts place by screen point. Early the next frame (order −10000), every bent part goes back exactly as it was. Maths in `Geometry/HudBend.cs`; `dump-hud` shows the layout. Two rules came out of a flash that took six builds to pin down. First, the game's floating origin carries the HUD's canvas a world shift away in the camera manager's LateUpdate, and the canvas is back over the window before it draws ([game-internals.md](game-internals.md)). So the bender never writes a screen point as a world position: `Rig/CanvasPlacement.cs` works out each piece's place in its canvas from where the canvas draws. Second, the aircraft can change under the same HUD at a respawn, so the cockpit is read from the game's HUD every frame.
- **Straight ahead** (`Rig/StraightAhead.cs`, behind `Hud.FollowStraightAhead`, on by default). Everything the game pins to the world goes through the main camera's projection and follows the view, and screen-fixed UI stays put. But a few HUD pieces take the window's middle to be straight ahead, and with an eye height set the center screen draws straight ahead elsewhere. The target designator is the view-center diamond: targeting takes the markers nearest it on screen. Every frame it's put at straight ahead, its place worked out from the screen point alone (`CanvasPlacement`), never relative to where it sits. Relative moves stacked a second move onto copies of an already moved HUD at a respawn. When following stops, it goes back to the place the game first gave it. Two postfixes re-pin the off-screen arrows along the line from straight ahead: `Patches/OffScreenArrowPatch.cs` on the shared pin, and `Patches/ObjectiveArrowPatch.cs` on the objective markers' own copy of it (maths in `Geometry/EdgePin.cs`). The helmet display and the airbase capture panel stay where the game lays them out. The helmet panels hide while the flight HUD's anchor is near, which works either way. The capture panel sits near the top of the window; moving it up by the eye height pushed it off the top (0.1.12 to 0.1.18). Where straight ahead sits at the window's middle, nothing changes. The diamond's hiding is the game's own rule: with a gun selected, it hides on that gun's cross, wherever the gun points (often a few degrees below the nose); with a missile or no weapon, it hides on the W.
- **Menus on the center screen** (`Rig/MenuPinning.cs`, behind `Window.MenusOnCenter`, on by default). A screen-overlay canvas covers the whole window, so menus anchored to its edges landed on the outer screens. That put the main menu's buttons on the far left, and the loadout screen's ribbons and rows across all three; a canvas that scales with the window's width, as Rewired's control mapper does, grew about 2.6×. While the window is spanned, in missions or in the main menu, every root screen-overlay canvas has the anchors of its top-level pieces remapped into the center screen's share of the window. The flight HUD, the blackout fade and UnityExplorer's canvases are left out. A canvas whose scale would differ gets the scale it would have on that screen alone (maths in `Geometry/MenuFit.cs`). Each piece carries a marker holding the anchors the game gave it, so a copy made at runtime is pinned from those and never twice. Canvases are found once a second, inactive ones included, and new top-level pieces are pinned the frame they appear. Off, or unspanned, everything goes back as the game made it. The loadout screen's backdrop, the rotating aircraft view, is a camera, so it still fills all three screens. A menu background sized to cover the screen at its own aspect, like the main menu's aircraft picture, spills a little onto the side screens where a single screen would crop it.
- **HUD corner panels** (`Rig/HudCorners.cs`, `Hud.CornerPanels`, CenterScreen by default). The overhead map with the threat list (bottom left) and the weapons, power and countermeasures panel (top right) sit in the helmet frame (`HMDCenter`), which the game sizes to the window's width. The damage display (bottom right) sits on the HUD's canvas. Their anchors are remapped into the part of each parent the center screen covers, worked out from where the canvas draws, so they land in the center screen's corners whatever the helmet frame's size. They use the menu pinning's markers. OuterCorners keeps the game's layout, on the side screens' outer corners.
- **The main menu's mark** (`Rig/MenuLogo.cs`, behind `Window.MenuLogo`, on by default; 0.1.30). A small, faint copy of the project mark in the main menu's bottom-right corner: 54 canvas units tall, 24 in from the corner, at 55% opacity. It's a child of the game's main menu panel (the object with the game's `MainMenu` component), added as its last child, so it draws over the panel's background but under the settings screen and popups, which sit above that panel; it takes no clicks. The menu pinning keeps the panel on the center screen, so the mark lands in that screen's corner. There's no image file: the plugin embeds `branding/nuclear-triad-mark-white.svg` and draws it at the size it shows, again whenever that changes. `Geometry/MarkShape.cs` reads the one even-odd path `tools/logo.py` writes, turns its arcs into short chords, and works out each pixel's coverage along eight lines per row. Off, the piece is destroyed.

## World

- **Trees and grass.** The game culls them on the GPU once a frame against global planes made from the main camera, the center screen alone, then draws the survivors for every camera. A Harmony postfix (`Patches/VegetationCullPatch.cs`) on the call that sets those planes replaces them with planes holding every screen's lit area plus `Vegetation.CullMarginDeg` (10° by default; geometry in `Geometry/CullPlanes.cs`). It sits behind `Vegetation.CullAllScreens`.

## The window

- The window span is one setting: center band (as tall as the center screen; the default, because the game scales its HUD and menus to window height), full height (bounding box of all screens) or an explicit desktop rect. In band mode, black curtain windows cover the side screens' uncovered strips.
- Each viewport is its monitor's rect intersected with the game window's client rect, normalized to Unity's bottom-left origin. When the window covers only part of a monitor, the frustum covers only that part of the panel (`Panel.Sub`). Monitor rects come from `EnumDisplayMonitors` and `GetMonitorInfo`; the client rect from `GetClientRect` plus `ClientToScreen`. Config also accepts explicit pixel rects, for NVIDIA Surround.

## Lifecycle and timing

- Apply rig state as late as possible: in `RenderPipelineManager.beginContextRendering`, once a frame before any camera renders. The flight HUD bend and eye hold run in LateUpdate at order 10000, after the game's camera manager.
- Build the rig when a mission scene loads and `CameraStateManager` exists, and destroy it on unload. Toggle-off destroys the side cameras and restores the game cameras' full-window rects, `ResetProjectionMatrix()` and the original FOV. The rig needs both `Rig.Enabled` and the runtime toggle. The toggle starts from `Rig.Enabled`, and turning `Rig.Enabled` on switches it on too (0.1.26), so the setting alone brings the rig up.
- **BepInEx's manager object** (`BepInExSetup.cs`, behind `Setup.FixBepInExManager`, on by default; 0.1.28). The game removes the object every plugin sits on unless BepInEx hides it, which BepInEx does only with `[Chainloader] HideManagerGameObject = true`, off in a new install ([game-internals.md](game-internals.md)). BepInEx creates the object and loads every plugin onto it in one go, before the game's first scene, so in `Plugin.Awake` the plugin hides it, as the setting would, and that start works. It then turns the setting on through BepInEx's own config object, which is internal and reached by reflection, so BepInEx writes its file as it does at every start and hides the object itself from then on. One log warning says what changed. Off: BepInEx is left as it is.

## Settings and F1

- Every behavior sits behind a config flag and the runtime toggle. Toggle-off equals vanilla.
- F1's layout (0.1.23). ConfigurationManager 19 lists a plugin's sections in the order it first binds a visible setting in each, and settings by Order, which `RigConfig` counts down as it binds. So `RigConfig`'s binding order is the layout. The cfg file sorts sections by name, so descriptions never say "above" or "below". F1 opens on a Start here box, `Geometry.Tuner`'s custom drawer (`Tuning/StartHere.cs`). It says to do this first, and its button opens the tuner and closes F1, whose window would cover the tuner's. Then the simple settings: each screen's `Monitor` and `WidthMm`, and each side's `GapMm`, `AngleDeg` and `VerticalOffsetMm`; `Geometry.Measured`, `EyeHeightMm` and `SkyGrid`; `Window.Span`; and the tuner, grid and toggle hotkeys. Everything else is advanced, with the Rig, Hud, Vegetation, Setup and Dev sections last. A setting is simple only if someone setting up a rig needs it. No key has been renamed. BepInEx writes back every key it can't bind, so a key no build reads goes in `RigConfig.Retired`, which drops it from the cfg once.
